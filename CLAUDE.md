# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A standalone, embeddable chat-widget for **EveryParts / PartsMind**: a "search assistant" that lets a shop visitor describe their equipment and the part they need in natural language, and returns compatible products. The widget is delivered to client shops as a single `<script>` tag and talks to a separate EveryParts search API (not part of this repo) over HTTPS/JSON.

The entire widget is one self-contained, dependency-free file: `everyparts-widget.js`. `everyparts-widget.min.js` is a minified build of the same file. **There is no package.json, linter, or bundler in this repo** — it's plain vanilla JS. Tests are stand-alone HTML pages under `tests/`, opened in a browser (`?scenario=…` where a page has several) and reporting through `window.__EP_TEST__`. Run `./tools/release.sh <version>` to rebuild: it re-minifies the widget (`terser -c -m`, no trailing newline — the convention that reproduces the existing build byte-for-byte), computes its SHA-384 SRI, and exports `everyparts-widget.i18n.json` (`tools/dump-i18n.mjs`, which brace-matches the `I18N` literal out of the source and evaluates it in an empty context). The hub imports that dictionary with the engine: it is how the hub knows which keys exist and which texts are the defaults, so that a site is served only what differs from them. Committing a build without it leaves the hub computing overrides against the previous engine's texts. `./tools/release.sh verify <version>` checks that the tag pushed to GitHub serves that exact content. Editing `everyparts-widget.js` without rebuilding leaves `.min.js` stale; a comment-only edit is the exception, since `terser` strips comments and leaves the minified output unchanged — confirm with a throwaway rebuild rather than assuming it.

## Delivery: two-tier loader (cache invalidation)

Shops embed a single `<script src="…/widget/v1/w.js?t=TOKEN">` tag, generated by the delivery hub (`everyparts-api-hub`). A shop's `<script src>` never changes, and an entry already in a browser cache is unreachable — no CDN purge and no later header can invalidate it. Only what was sent at download time matters, hence two tiers:

- **Tier 1 — the loader**, `GET /widget/v1/w.js?t=TOKEN`, generated by the hub on every request (`WidgetLoaderScript`) with `Cache-Control: no-cache`. Revalidated every page load (a ~150-byte 304). It carries the current widget URL + SRI hash, read from the hub's manifest of imported versions.
- **Tier 2 — this widget**, `GET /widget/v1/engine/{version}.js`, served `immutable, max-age=31536000` by the hub, from a copy it imported via `widget:engine:import`. Downloaded once per visitor, never revalidated.

Both tiers are hosted and generated by the hub; `tools/release.sh` in this repo only minifies the source, computes its SRI, tags the release, and confirms GitHub serves what was tagged.

The loader copies the snippet's `data-*` attributes onto the script tag it injects, so this widget's own `document.currentScript` resolution ([everyparts-widget.js:21](everyparts-widget.js:21)) keeps working untouched. SRI is safe here *because* the URL is pinned; an SRI mismatch fails closed (widget absent) with a loud console error naming the cause.

Tags carry **no `v` prefix** (`1.0.9`, `1.1.1`, …): the version is used literally as a git ref, both by `tools/release.sh verify` (via `raw.githubusercontent.com`) and by the hub's `widget:engine:import` — a prefix would break both. And **never reuse a version number**: an imported version is served `immutable`, so republishing a tag redistributes nothing — the hub and every browser that already downloaded it keep serving the old bytes, silently and forever. `release.sh` refuses a version that already exists on `origin` and names the next free one; the hub separately refuses to reimport a version it already has.

Release order matters — the import references a tag that must already be published:
1. `./tools/release.sh <version>` (names the next free version if you guess wrong)
2. commit, `git tag <version>`, `git push origin <version>`
3. `./tools/release.sh verify <version>` — fetches the published file from GitHub, asserts the SRI matches, then calls `notify_hub` to trigger the import over HTTP, reading `HUB_ENGINE_IMPORT_URL` / `HUB_ENGINE_IMPORT_SECRET` from `.env.release` (untracked — copy `.env.release.example`) or the environment; neither set, it just prints the command to run by hand
4. on the hub: `widget:engine:enable <version>` — or pin it to a single site as a canary

A shop's widget goes stale for at most one page load. Don't ship a breaking `/search` contract change and a widget release in the same instant.

The pages under `tests/` cover the flows they name and stub `fetch` themselves; run the ones your change touches. Anything they do not cover is verified by loading the widget in a real HTML page against a running (or mocked) instance of the API and exercising the flows by hand (open/close, search, clarification, refinement, pagination, review prompt).

## Integration contract

The widget self-initializes from its own `<script>` tag's `data-*` attributes (read via `document.currentScript`, with a fallback lookup for `script[data-token]` if the script was loaded async/deferred and `currentScript` is unavailable). Since 1.3.0 `data-*` is no longer the *only* source — see **Per-site config from the hub** below for the piece the server can reach that attributes can't: i18n wordings.

- `data-token` — site token, sent as `Authorization: Bearer <token>`.
- `data-locale` (falls back to legacy `data-lang`) — BCP-47 locale; resolved against supported locales, then `navigator.languages`, then defaults to `fr-FR`.
- `data-position` — `bottom-right` (default) / `bottom-left` / `top-right` / `top-left`.
- `data-api` — API base URL (defaults to `http://localhost:8000/api/v1` for local dev against a mock API).
- `data-logo` (optional) — URL of a shop logo image. When set (or `data-title` is set), it **replaces** the default EveryParts wordmark in the header; EveryParts attribution remains in the "Powered by" footer. Built by `headerBrandHtml()`.
- `data-title` (optional) — shop name shown as text in the header. `data-logo` alone → image; `data-title` alone → title text; both → image + title. Neither (nor `data-subtitle`) → default EveryParts logo.
- `data-subtitle` (optional) — secondary line shown under `data-title` in a smaller, lighter font (`#ep-header-subtitle`). Rendered inside the stacked `#ep-header-text` block by `headerBrandHtml()`.
- `data-contact-page-url` (optional) — URL of the shop's contact page. It is what a `[link]…[/link]` tag resolves to, in a server message as well as in the `welcome_p3` welcome line (which is only rendered when this attribute is set). Unset, link tags degrade to plain text — see the security note.
- `data-debug` (optional, defaults to **off**) — logs the whole telemetry cycle to the console, prefixed `[PartsMind]`: every event queued with its payload and session, every drop at validation, each flush, and every server refusal including `meta.ignored` (the signal that catches a mistyped field name). Off means *silent* — a test asserts nothing is written without the attribute. See [TELEMETRY.md](TELEMETRY.md).
- `data-enable-parts-request` (optional, defaults to **on**) — set to `"false"` (or `"0"`) to suppress the part-request flow entirely. An off switch, not an opt-in: existing snippets keep the feature without being touched. Parsed by `boolAttr()`, which treats a bare attribute as `true` (like native HTML booleans) and falls back to the default on an unrecognised value rather than reading it as `false` — a typo must not silently disable a feature. Exposed as `CONFIG.partsRequest` and checked in exactly two places: the `renderNoResults()` call site, and the `pr_offer` branch of `replayEntry()`, so a conversation journalled while the feature was on does not resurrect the offer after it is switched off. When off, `renderNoResults()` still emits the `after_parts_request` follow-up — `showAfterPartsRequest(null)`, no entry to dedupe against since it runs once per response — otherwise the conversation would simply stall on the failed search. The sheet's markup is still emitted but stays inert — gating the two entry points is far less risky than making every DOM reference nullable.

It talks to three endpoints (plus telemetry — see [TELEMETRY.md](TELEMETRY.md) and the `Telemetry` module):
- `POST {apiBase}/search` — the single conversational endpoint. Every user message, clarification-button click, and refinement answer goes through this same endpoint with `{ query, session_id, context }` (plus `pagination` or `refinement` extras where relevant). The response's `type` field (`results` | `clarification` | `no_results` | `error`) is the discriminant the widget renders on — see `renderResponse()`.
- `POST {apiBase}/review` — best-effort satisfaction vote (thumbs up/down), fire-and-forget, never blocks the UI. A **thumbs-down sends twice**: the bare vote on click, then a second call carrying `comment` once the user picks a reason. The four reasons render under the prompt (`renderReviewReasons()`); the first three post their own label as `comment`, while *Autre, préciser* opens a bottom sheet (`#ep-rv-backdrop`, the same `.ep-sheet-*` dressing as the part-request sheet) with a 200-char textarea whose free text becomes the `comment`. Cancelling sends nothing and leaves the reasons clickable. The chosen reason is journalled on the `review` entry (`reason`, plus `reasonText` for the free text), so a reload restores the group frozen on that choice instead of asking again — which is why `replayEntry` passes the entry even for an already-answered review.

Conversation state (`sessionId`, `conversationContext.previous_clarifications`) is held in page-memory closures but is **also persisted client-side** to `localStorage` (key `everyparts-chat:<token>`, 30-min inactivity TTL) so it survives navigation and new tabs — see the persistence section below. No assumption should be made that the *server* remembers anything the widget doesn't re-send (aside from paginated list state keyed by `session_id`, which the server may expire — see the `pagination_expired` handling in `fetchNextPage`).

### Per-site config from the hub (`window.__PARTSMIND_CONFIG__`)

The hub (everyparts-api-hub) serves each site's configuration *with the loader* it generates (`GET /widget/v1/w.js?t=TOKEN`), and exposes it as `window.__PARTSMIND_CONFIG__` before this engine loads:

```js
window.__PARTSMIND_CONFIG__ = {
  attributes: { "data-token": "...", ... },  // already applied to the <script> tag by the loader — the engine never reads this
  theme:      { "--ep-primary": "#E5006D" }, // already applied as a page-level CSS rule by the loader (it beats :host) — the engine never applies this itself
  wordings:   { "fr-FR": { "welcome_p1": "…", "placeholder": "…" } },
  icon:       { path: "M20.59 13.41 …" },    // or { url: "https://…/icon.svg" }, or null for none
  avatar:     "https://…/shop-logo.png",     // assistant avatar; empty = the EveryParts mark
};
```

Of the five keys, **only `wordings`, `icon` and `avatar` are the engine's concern** — `attributes` and `theme` are already in effect by the time this script runs, and re-applying either here would be a second place to maintain a single effect. `wordings` is what the server *can't* reach any other way: a locale → i18n-key → text map layered on top of the built-in `I18N` dictionary, read into `CONFIG.wordings` (empty object if the global is absent, not an object, or has no `wordings` key — an old integration, or a page with no hub-delivered config, must behave exactly as before).

`t(key, vars)` and `tList(key)` consult `CONFIG.wordings[CONFIG.locale][key]` **above** `I18N`, never instead of it: a key the server didn't rewrite still falls through to `I18N[CONFIG.locale]`, then to `I18N['fr-FR']`, then to the bare key — the existing fallback chain is untouched, just given a new head. `tList()` only accepts a rewrite that is itself an array; anything else (a server sending a string for a list-shaped key) is ignored, not coerced. Since the server can add rewritten keys at any time without telling the engine, `wordings` must be treated as a generic override layer — never hard-coded to the handful of keys it happens to rewrite today (`welcome_p1`, `welcome_p2`, `placeholder`, at last count).

`icon` is the glyph of the context bar, which the hub serves per business universe. It arrives in one of two shapes and **neither is markup**: `path` is the `d` data of an SVG path, which the engine sets on a `<path>` it builds itself with `createElementNS` under a fixed `viewBox` and `fill` — a `d` that is not pure geometry (`SVG_PATH_RE`) is ignored rather than rendered; `url` is an address rendered as an `<img>`, the same channel as `data-logo`. `null` renders no icon box at all, and an absent key leaves the engine's own neutral glyph (`SUBJECT_ICON_PATH`). This is what lets a universe ship its own icon while the rule below — the server never sends HTML — stays intact, and it is why no SVG sanitiser is needed anywhere in this file.

`avatar` is the image drawn on **every assistant message** (`paintAvatar()`, `.ep-msg-avatar`). A plain URL rather than `icon`'s two shapes: a merchant's logo is multi-path and multi-colour, which path data cannot carry. It is rendered as an `<img>` through `escHtml()`, and when set the badge drops its dark background — that background exists to make the EveryParts mark stand out and would swallow a light logo.

**The floating launcher keeps the EveryParts mark, deliberately** (`markSvg()` at the two `#ep-fab` call sites): it announces the product, not the merchant. The header is not driven by `avatar` either — `data-logo` already governs it, and pointing two settings at one element would be two places to maintain a single effect.

This turns **every** i18n key into potentially server-controlled text, which is why every `t(...)` call interpolated into an HTML template string — attribute or element content — goes through `escHtml()` (see the security note below); one that lands via `.textContent`/`.title`/`element.setAttribute(...)` needs no such wrapping, since none of those parse HTML.

## Architecture (single IIFE in `everyparts-widget.js`)

Everything lives inside one top-level IIFE. Reading order to get oriented:

1. **Config & i18n** — `CONFIG` object resolved from script attributes, plus `CONFIG.wordings` from the hub's `window.__PARTSMIND_CONFIG__` (see **Per-site config from the hub** above); `I18N` dict keyed by locale (`fr-FR`, `en-US`, `en-GB`) with a `t(key, vars)` lookup helper that checks `wordings` first. When adding a new user-facing string, add the key to **all three** locale objects, not just `fr-FR` — `t()` falls back to `fr-FR` for missing keys, so a forgotten translation fails silently into French. The dictionary names no business universe: the engine serves motorcycle, agricultural, nautical and appliance shops alike, and each universe's own vocabulary is served by the hub as `wordings`. A string here that says *moto* or *véhicule* ships that universe to every site that has not overridden it.
2. **`STYLES`** — the entire CSS for the Shadow DOM as a template string. Mobile-first: `#ep-window` is full-viewport by default (anchored to all four edges rather than using `100vh`, to dodge mobile browser chrome quirks) and becomes a floating card only above the `641px` breakpoint. All themable values are CSS custom properties prefixed `--ep-` (colors, fonts, radius, shadow) — respect the existing palette/variable names rather than hardcoding new colors.
3. **Module-level conversation state**: `sessionId` (generated UUID), `conversationContext`, `isLoading`, `lastClarificationField`, `pendingRefinement`, `activeList`, `identifiedVehicle`, plus persistence state `transcript` and `isRestoring`. These are mutable closures shared across the functions below — there's no store/class, just shared state in the IIFE scope.
4. **`mount()`** — builds the Shadow DOM (`host.attachShadow({ mode: 'open' })`), injects styles, the floating action button, and the chat window, and wires up all event listeners. Almost all of the interactive logic (message sending, rendering, pagination, refinement) is defined as nested functions inside `mount()`, closing over its local DOM references (`messagesEl`, `inputEl`, etc.) rather than being passed around as parameters.

### Header, welcome chips & the context bar (1a redesign)

The header (light "1a" direction) shows a gradient "e" **avatar** with an online-status dot (`AVATAR_HTML`, hidden when a custom `data-logo` is set so shop branding isn't doubled), the configurable brand (`headerBrandHtml()`), and icon-only reset/close buttons using the redrawn 24-grid / 1.7-stroke icon set.

The welcome message (`showWelcome()`) renders the greeting bubble plus a row of clickable **suggestion chips** (`renderTryChips()`, from the `try_chips` i18n array via `tList()`). Chips are onboarding-only and **not** persisted: a click (or any manual send) calls `removeTryChips()` and runs that search; on restore they never reappear.

The persistent **context bar** (`#ep-subject-bar`, pinned above the input) is driven by the server's `interpreted` object (`manufacturer`/`model`/`year`) present on every `/search` response. `updateVehicleFromData()` (called at the top of `renderResponse()`) sets `identifiedVehicle` once manufacturer + model are known; `renderSubjectBar()` shows/formats it ("Honda CBR 600 F · 1996"); it's persisted in `localStorage` (schema v4) and restored on mount. Its glyph is set once at mount by `renderSubjectIcon()`, from `CONFIG.icon` (see **Per-site config from the hub**). The **Modifier** button (`editSubject()`) clears `identifiedVehicle` **and** `conversationContext.previous_clarifications`, then focuses the input so the user re-describes their equipment.

### Floating launcher: closed ⇄ expanded (5a / 4a frames)

`#ep-fab` is a single `<button>` holding **three absolutely-positioned layers** (`.ep-fab-layer`, all `inset: 0` + `pointer-events: none`) that cross-fade in **opacity** — never `display`, which would make the morph jump:

- `.ep-fab-closed` — round teal bubble (60×58, `border-radius: 29px`): white everyparts monogram + unread counter.
- `.ep-fab-face` — the expanded search facade: a **white** pill ringed in teal, holding a grey magnifier, a well of cycling example queries, and a **teal** 46px disc carrying the white monogram + counter.
- `.ep-fab-chevron` — the "collapse" chevron, shown while the chat window is open (`.ep-window-open`).

The two states have **different surfaces**, not just different content — each layer paints its own background, so the morph is teal-bubble → white-field. Three consequences:

- `#ep-fab` itself keeps a permanent teal background. The frame instead leaves the container transparent and stacks two opaque layers, which bleeds ~25% of the page through the pill at the midpoint of the cross-fade — invisible on the design canvas, ugly over an arbitrary shop page. The teal base closes that hole and is also what the chevron state sits on.
- The face needs `overflow: hidden` because its ~113px of minimum content does not fit a still-narrow pill; without it the disc spills up to 47px past the anchored edge during the first ~400ms.
- **The face's counter therefore lives in its own layer** (`.ep-fab-face-badge`), outside that clip, fading on the identical schedule. It is *meant* to overhang the rounded corner: at 1px from the top a 29px radius leaves the pill's surface reaching only ~21px in from the right edge, while the counter reaches 2px — so `overflow: hidden` sliced it clean off. Same reason its offsets are `top: 1px; right: 2px` against the pill rather than the frame's `-5px/-6px` against the disc: different containing block, same rendered position.

Only the **width** animates (60px ⇄ `min(372px, 100vw - 32px)`). The corner-anchored edge never moves, so the pill stretches inward from whichever side `data-position` picks — no per-position animation needed. Expansion takes 1.35s and collapse .54s, matching the frame's asymmetric loop; the two durations live on the base rule (collapse) and on `.ep-fab-expanded` (expand), since a transition is read off its *destination* state.

**Width and the two opacity fades must share the same window and the same easing** (1.35s `ease-in-out` on all three). The frame's `pmClosedFade`/`pmOpenedFade` are strict complements of `pmSwitchW`; any stagger between them — a shorter fade-out, a delayed fade-in — is immediately legible as "not the frame". Verify by sampling: the two layer opacities must sum to 1.000 on every frame.

The monogram comes from the design project's `everyparts-mark.svg`, inlined as `MARK_PATH` + `markSvg(w, h, color)` — the frames use it at two sizes/colors, hence the helper.

**State on page load** (`initClosedLauncher()`), chat closed:
- **Conversation already engaged** (`lastAssistantPreview()` returns a turn) → the launcher **stays a closed round bubble**, with the unread badge and the preview teaser bubble.
- **New visitor** (`!hasUserInteraction()`) → after `LAUNCHER_EXPAND_MS` (1s, matching 5a's delay) it expands and **stays expanded until the first click**. The frame's 9s open/close loop is canvas-demo only — do not port it.
- User typed but has no answer yet → nothing.

For new visitors, the expanded launcher itself draws the attention a teaser bubble would, in the same corner, at the same moment. The teaser mechanism is used only for the returning-conversation preview.

`toggleWindow(true)` calls `collapseLauncher()` so the pill folds back to a round bubble *while* the window opens, and clears any pending expand timer. Both counters (`.ep-fab-badge`, one per state — their anchors differ) are driven together by `showBadge()`/`hideBadge()` over a `querySelectorAll`.

Counter visibility is toggled in **opacity, not `display`**: each counter lives inside a layer that fades, and `display: none` would make it vanish in one frame instead of following its layer. On top of that, `#ep-fab.ep-fab-expanded .ep-fab-badge-bubble` forces the bubble counter to `opacity: 0` with `transition: none` — otherwise it flashes on the round bubble at the very start of the expansion, because `showBadge()` and `.ep-fab-expanded` land in the same tick and the closed layer is still opaque for another ~350ms.

The example queries cycle from the `launcher_examples` i18n array (3 entries per locale) via one 9s keyframe offset `-3s`/`-6s`, so exactly one shows at a time — frame 4a's text animation. The animation is bound to `.ep-fab-expanded`, so its phase starts at reveal rather than at page load. Under `prefers-reduced-motion` the launcher switches state instantly and the first example stays visible; those overrides must **match the specificity** of the state rules they neutralise, since a media query adds none.

### Response rendering flow

`sendMessage()` → `callSearch()` (POST `/search`) → `renderResponse()` (first calls `updateVehicleFromData()`) switches on `data.type`:
- `results` → `renderResults()`. If the payload includes `refinement.questions`, results are *withheld* and `startRefinement()` runs first (see below). Otherwise it renders the assistant message, the product list (`renderProductList()`), and — only when there are products — the satisfaction prompt (`renderReviewPrompt()`); otherwise it goes straight to the `after_result` prompt.
- `clarification` → `renderClarification()`: renders clickable option buttons/list (`appendOptionsGroup()`); picking one pushes into `conversationContext.previous_clarifications` and re-submits it as `callSearch(value)`. On a `part_type` question the widget appends its own **"Toutes les pièces"** option, which widens the search to the catalogue — **unless the response carries `contact_url`**: the server has then decided this request belongs with the shop's contact page, and offering to browse everything alongside would contradict the answer it just gave. What is journalled is what was shown, so a reload never brings the discarded option back.
- `no_results` → `renderNoResults()`: message plus optional suggestions list, then the part-request offer. The response may also carry the **other parts compatible with the identified vehicle** (`results` + `pagination`, same fields as a `results` payload) — they are not shown on arrival; they become the offer's alternative, see below. No `startNewSession()` runs here, so the `pr_offer` entry (and the products entry, if the list is revealed) capture the same session as the search.
- `error` → inline error bubble.

### Part request on `no_results` (frame 2a)

When `/search` answers `no_results`, `renderNoResults()` chains into
`renderPartsRequestOffer()` — an assistant bubble offering *Demander à un expert* /
*Non merci*. Nothing opens by itself; the modal sheet is strictly opt-in.

**Two cases, decided solely on whether the response carried other compatible parts**
(`data.results`, passed down as `renderPartsRequestOffer(reuseEntry, { products, pagination })`):
without them the offer reads `pr_offer` and declining just declines; with them it reads
`pr_offer_other_parts` and the decline button becomes `pr_offer_no_other_parts` ("Autres
pièces") — declining the expert *is* asking to see those parts, so the click renders them.
The list appears **only** on that click, ahead of the `after_parts_request` follow-up (which
invites the user to move on and therefore has nothing to precede).

Those parts are captured **on the `pr_offer` entry** (`otherParts`/`otherPagination`), exactly
like the vehicle and part: a replayed offer must keep its own copy, its own button label and
its own list, and stay revealable even after the conversation moved on — which is also why the
storage schema went to **v4**. Revealing them goes through `renderOtherParts()`, i.e. an
ordinary `renderProductList()` (toolbar, "load more", its own `products` transcript entry) with
one correction: `activeList.sessionId` is forced back to the entry's session, because "load
more" queries the server's paginated state for **the failed search**, not for whatever session
is current by then (a later results turn rotates it, and a reload restores it).

When `data-enable-parts-request` is off there is no offer and therefore no button to reveal
anything, so `renderNoResults()` renders the list straight away before the follow-up: it is the
part *request* that is switched off, not the display of products the API did return.

`#ep-pr-backdrop` is a bottom sheet living inside `#ep-window` (which is `position: fixed`
+ `overflow: hidden`, so it doubles as the containing block **and** clips the sheet sliding
up). The modal therefore never covers the host page — only the widget.

It carries three controls: the **part recall**, the email, and the RGPD consent. The recall
(`#ep-pr-message`, the green pill from frame 2a) is prefilled with
`"<identifiedPart> — <identifiedVehicle>"` and is **editable** — its value is what ships as the schema's `message`. A
pencil icon pinned to the pill's top-right corner (`.ep-pr-edit-icon`, `position: absolute`, decorative/`aria-hidden`)
is the only visual cue that the bold-styled recall text is editable rather than static — without it, the pill reads
like frozen summary content. It is a
`<textarea rows="1">` that auto-grows, not an `<input>`: at the 16px mobile size the prefilled
value runs past one line, and a single-line input would silently truncate the very text the
user is about to send. `Enter` submits rather than inserting a newline. Whitespace-only means
*absent*, so the key is omitted entirely — the schema sets `minLength: 1` alongside
`additionalProperties: false`, and an empty string would be rejected. `session_id` is always
present, so it alone satisfies the `anyOf` and `empty_request` stays unreachable — still
mapped, defensively.

The recall is built from **`identifiedPart`**, not from the raw query. `identifiedPart` is
module state fed by `updatePartFromData()` off `interpreted.part_type`, persisted next to
`identifiedVehicle` and captured onto the `pr_offer` entry — the exact same lifecycle as the
vehicle. Using the raw query instead duplicates the bike: `"guidon honda cbr 600 85"` plus
`"Honda CBR 600 F · 1985"` names the model twice. The raw query is only a fallback for when
the server did not classify a part, and in that case the vehicle is *not* appended — it is
almost certainly already in the text.

`POST {apiBase}/parts-request` — note the path has **no extra `/api/v1`**: `CONFIG.apiBase`
already ends in it. This call burns the tenant's rate limit and monthly quota exactly like a
search, so: one request per submit, submit disabled in flight, **no retry on any status**,
and the server does not deduplicate.

Error handling branches on `error.code`, never on the text; the *displayed* string is the
server's (French, user-presentable) with a local i18n fallback. `PR_ERROR_FIELDS` maps each
422 code to the field that shows it (`invalid_email`→email, `consent_required`→checkbox,
`empty_request`/`message_too_long`→the recall field), and `prShowError()` moves focus there. The
same rules are mirrored client-side so a well-formed UI never reaches a 422.

Two iOS-specific rules, both learned the hard way on the simulator and both already
established elsewhere in this file's codebase:
- `#ep-pr-email` and `#ep-pr-message` are **16px on mobile** (the frame's 13.5px/12.5px only
  above 641px). Under 16px, Safari zooms the page on focus and pans it sideways — the sheet
  ends up clipped. Same reason `#ep-input` is 16px.
- `openPartsRequest()` does **not** autofocus on mobile (`if (!isMobile())`), same rule as
  `toggleWindow()`: opening the keyboard immediately halves the sheet and hides the consent
  line before it can be read.

The offer is journalled as a `pr_offer` entry (`status`: `pending` | `declined` | `sent`,
plus the `sessionId`, vehicle, part and other compatible parts captured at creation — the
failed search's session, not whatever `startNewSession()` has moved on to). On 201 the entry flips to `sent`, the
buttons freeze and a confirmation is appended, so it can never be submitted twice.

**A `pending` offer replays live wherever it sits in the history** — the `review` rule, not
the options-group rule. *Yes* deliberately does not freeze the offer, so cancelling the sheet
must let the user come back to it; and the `after_parts_request` follow-up appended on click
means the offer is no longer the last entry, so an is-last test would strand anyone who
opened the sheet, cancelled, then reloaded. Each entry carries its own session/vehicle/part,
so reopening an older offer stays bound to the right search.

The `after_parts_request` follow-up fires on the **terminal outcomes only** — declining, and
the 201, where it comes *after* `pr_success` so the confirmation is never preceded by an
invitation to move on. *Yes* itself appends nothing: it merely opens the sheet.
`showAfterPartsRequest(entry)` guards on a persisted `afterShown` flag, so a
*Yes → Cancel → Yes* round trip never appends a second copy into the DOM or the transcript —
the invariant holds at one per offer across both call sites and across a reload.

Every focus inside the sheet uses `focus({ preventScroll: true })`, including the one that
returns focus to the trigger on close. `#ep-window` is programmatically scrollable despite
`overflow: hidden`, so a scroll-into-view there shifts the whole panel — and the offset
outlives the sheet, leaving the header cropped. `closePartsRequest()` also resets
`win.scrollTop` as a backstop; the message list keeps its own scroll position.

### Refinement chain (`pendingRefinement`)

When the server wants to narrow down a large result set before showing it, it attaches `refinement.questions` to a `results` response. The widget asks each question **in sequence** (`askRefinementQuestion()` / `recordRefinementAnswer()`), always with an added "I don't know" option, entirely client-side — no network calls between questions. Only at the end (`finishRefinement()`) does it either fire a single new `/search` call with all collected answers, or — if every answer was "I don't know" — fall back to rendering the original (already-fetched) result set with no extra request. While a refinement is pending, free-text input typed into the chat is treated as an answer to the current question rather than a new search (see the `pendingRefinement` branch in `sendMessage()`).

### Paginated product lists (`activeList`)

Only **one** paginated list is "live" at a time — module state `activeList` tracks its entries, DOM elements, and pagination cursor. Starting a new search removes the previous list's "load more" button (`renderProductList()`), since clicking a stale button would append new-search results into the wrong list. `fetchNextPage()` requests the next page via `/search` with `{ session_id, pagination: { page } }` and appends to the *same* list/toolbar rather than creating a new message bubble; a `pagination_expired` error from the server replaces the button with an inline "list expired, search again" note. New entries are pushed through the toolbar's `enrich()`/`apply()` so filter/sort/count stay correct after "load more".

### Products toolbar & clarification lists — shared thresholds

Three module-level constants gate progressive disclosure of UI complexity:
- `CLARI_CHIPS_MAX` (6) — beyond this many clarification options, `appendOptionsGroup()` switches from horizontal chip buttons to a scrollable vertical list.
- `CLARI_FILTER_MIN` (8) — beyond this many options, a text filter input is added above the list.
- `PRODUCTS_TOOLBAR_MIN` (5) — beyond this many *total* results (not just the current page — decided off `pagination.total` so page 1 never falsely triggers it), `buildProductsToolbar()` adds a combined filter+sort bar (filters by name/brand/ref via `normStr()` accent/case-insensitive matching; sorts by relevance/price/name using `Intl.Collator`). The toolbar uses an `IntersectionObserver` on a sentinel element to toggle a "stuck" shadow when it sticks to the top during scroll.

### Scroll framing & the "new messages" pill

One response turn appends **several** top-level blocks at once (assistant message, product list, review prompt, follow-up). Jumping to the last one scrolls straight past what should be read first, so the widget instead frames the **first** new block at the top of the visible area, and a floating pill announces whatever is left below.

`scrollBottom()` is the single call every renderer makes, and it doesn't scroll directly: it coalesces the burst of calls of one turn into **one** decision, taken in a `requestAnimationFrame` (`applyScroll()`). What was appended is collected by a **`MutationObserver`** on `#ep-messages` (`childList`, no subtree) rather than at the ~13 call sites — a block added later can't escape the count by forgetting to declare itself. The typing indicator is excluded; it isn't a message.

Three outcomes:
- **history replay** (`isRestoring` at call time — note the burst resolves *after* `restoreConversation()` has already reset the flag, hence the capture in `scrollBottom()`): the whole thread is "added" at once and there is no first new message to frame — it opens at the bottom, instantly, nothing unread.
- **user's own message** (`scrollBottom(true)` from `appendUserMessage`): brings the view back to the thread wherever it had scrolled, and clears the unread count. It then falls through to the general framing, so a response landing in the same frame as the message frames *the message*.
- **anything else**: if the user was pinned near the bottom (`AT_BOTTOM_EPS`), the first new block is framed 8px from the top and the rest of the turn becomes the unread set; if the user had scrolled up to read, **the view does not move** and the pill announces the arrival. Since the scroll is clamped to the end of the thread, a turn that fits on screen behaves exactly as before — it just goes to the bottom.

The pill (`#ep-jump`) has three states, decided by `updateJump()`: **"n nouveaux messages" + arrow**, centered, whenever something unread sits out of view; **arrow only**, round and parked on the right (so it hides as little as possible of what is being re-read), when nothing is unread but the user is more than `JUMP_MIN_OFFSET` from the end; absent otherwise. Clicking it goes to the end. It lives inside `#ep-conv`, a wrapper that exists *only* to position it: `#ep-conv` occupies exactly the scrolling area, so a plain `bottom: 8px` puts the pill just above whatever follows the conversation — the context bar when visible, the input area otherwise — with no measuring of a bottom stack whose height changes with the bar, the keyboard and the safe-areas.

Two traps, both because `scroll-behavior: smooth` makes the scroll **asynchronous**, and both of which showed up as visible glitches on the right-parked pill:
- The state must be decided on the scroll **target**, never on `messagesEl.scrollTop` — at the moment of a click on the pill, `scrollTop` hasn't moved yet, and nothing re-reads it once the animation lands (the final `scroll` event falls inside the ignored window), so the pill stayed on screen forever. `programScroll()` records `progTarget`, and `updateJump()` measures against it while `progActive()`.
- While the pill fades **out**, `updateJump()` returns after toggling `ep-visible` off: it retouches neither the shape class nor the label. Resetting it to "centered, empty" made the right-parked pill visibly travel back to the center mid-fade. For the same reason centering is done in layout (`left: 0; right: 0; margin: 0 auto; width: fit-content`) rather than with `translateX(-50%)`: the transform then carries only the fade's vertical offset, identical in both shapes, so a shape change is a plain position jump and never an animated horizontal slide.

A block stops being unread once it has appeared **in full**: a 1500px product list showing only its first rows is still to be read, and that is exactly what the pill is for. "Appeared" is tracked as `seenBottom`, the lowest point of the thread ever exposed — **monotonic**, so the count can only decrease and never flickers frame by frame while an animated scroll travels to its target. For the same reason `programScroll()` sets `atBottom`/`seenBottom` once, at the target, and `scroll` events are ignored for `PROG_SCROLL_MS` afterwards (they are our own animation, not the user leaving the bottom) — a `wheel`/`touchstart`/`mousedown`/`keydown` on the thread hands that trust straight back (`mousedown` for a scrollbar drag, which emits neither of the first two and may end before the window does). Those listeners sit on the scrolling area, which the pill is *not* a descendant of — it lives in `#ep-conv` — so clicking it doesn't trip them.

Consequences worth keeping in mind when touching this: the module's mutable state is declared **before** the first render (`showWelcome`/`restoreConversation` run from `mount()` and would hit a TDZ error otherwise); `newConversation()` must call `resetScrollState()`, since offsets restart at 0 after the thread is emptied and an inherited `seenBottom` would mark everything as read; and content grafted *inside* an existing block (a "load more" page) produces no new top-level child, hence no framing decision — `fetchNextPage` just calls `updateJump()` because the thread got longer.

### Session persistence (`transcript` + `localStorage`)

The conversation survives navigation (page-to-page, new tab, brief return) by persisting a serializable **`transcript`** — an ordered log of committed turns — to `localStorage` under `everyparts-chat:<token>`, with a 30-min inactivity TTL (`SESSION_TTL_MS`). The transcript, not the DOM, is the source of truth for what's on screen.

- **Logging** happens at commit points: `appendUserMessage`/`appendAssistantMessage` log text bubbles; `renderProductList`, `appendOptionsGroup`, `renderReviewPrompt`, and `renderNoResults` push their own richer entry types. Interactive selections (clarification/refinement choice, review vote) and "load more" pages mutate the already-logged entry in place, then `saveState()`. Transient content (error bubbles, typing indicator, `pagination_expired` note) is deliberately **not** persisted — restoring a stale error would be faking current state.
- **Restore** runs in `mount()` via `restoreConversation()` → `replayEntry(entry, isLast)`, which re-renders each entry through the existing renderers with **`isRestoring = true`** (gating every log + `saveState`, so replay is inert — no re-logging, no network). Resolved interactive controls (an answered clarification/refinement, a cast review vote) restore **frozen** (disabled, selection marked) via `appendOptionsGroup`'s `freeze()` and the `restoreSelectedIndex`/`restoreRating` params.
  - **Exception:** if the very **last** transcript entry is an `options` or `review` entry that was never answered, `replayEntry` restores it **live** instead — `resumeOptionsLive()` reconnects a clarification or refinement question to its real `onSelect` (for a refinement question, first rebuilding `pendingRefinement` from the entry's persisted `refinementSnapshot`: `{ data, answers }`), and `renderReviewPrompt(undefined, entry)` leaves the thumbs clickable. Both pass the **same already-persisted transcript entry** as `reuseEntry`/`opts.reuseEntry` rather than logging a new one, so a click after restore mutates that entry in place instead of writing into a dangling closure. An unanswered entry that is *not* last (superseded because the user moved on without answering it) still restores frozen — only the single still-open question at the true end of history is ever live.
- **`saveState`/`loadState`/`clearState`** wrap `localStorage` in try/catch: private mode, quota, or disabled storage degrade silently to in-memory (current behavior) without throwing. `loadState` discards payloads on version/token mismatch or expired TTL.
- The **"New conversation"** header button (`#ep-reset-btn` → `newConversation()`) clears the DOM, resets all state, calls `clearState()`, and re-shows the welcome — the escape hatch from a persisted conversation. `sessionId` is only regenerated if the session being left has sent at least one message (`rotateSession()`, see TELEMETRY.md) — spamming the button on an untouched conversation reuses the same id and emits no telemetry, while the visual reset still runs every time.

When adding a new kind of rendered content, decide whether it's conversational (log it + handle it in `replayEntry`) or transient (don't), and gate any new logging/`saveState` on `!isRestoring`.

### Security note

All server-supplied strings interpolated into `innerHTML` (product names, brands, refs, suggestions) go through `escHtml()`. Any new code path that injects API-provided text into HTML must do the same — `textContent` assignment is preferred wherever raw HTML isn't otherwise needed. Since `t(...)` can return a hub-supplied rewrite (`CONFIG.wordings`, see above), that rule now covers `t(...)` itself: every interpolation of a `t(...)` result into an HTML template string is wrapped in `escHtml()`, even for keys that look like static repo constants — the point of `wordings` is precisely that any key can stop being one.

**The one markup the server is allowed to emit is a link**, as `[link]libellé[/link]` — the server writes the label, and the href resolves through `linkHref()`: the **response's own `contact_url`** first (the server knows better than the configuration where *this* request should go), the shop's `data-contact-page-url` otherwise. `setLinkedText(el, text)` is the single door: `textContent` when there is no tag, and otherwise `linkTagHtml()`, whose whole point is the **order** — escape first (the text is untrusted), substitute the tag second. The reverse would have `escHtml()` neutralise the `<a>` that was just built. It is used by `appendAssistantMessage()` (so results, clarification, refinement and follow-up messages), `buildNoResults()`, `appendErrorMessage()` and the `welcome_p3` i18n string. Each of those takes the response's `contact_url` alongside the text and **persists it on the entry** (`contactUrl`, schema v5): the link belongs to *that message*, not to the conversation — a later response can point somewhere else, and replay must give every bubble back its own target. What is journalled is otherwise the **raw** text, tag included, so replay rebuilds the same link through the same function. A server-sent href is trusted and merely escaped, exactly like the `url` of a product card. With neither URL the tag is dropped and the label stays as plain text — the sentence still reads, it just isn't clickable, rather than showing a raw `[link]` on a shop's page; a malformed (unclosed) tag matches nothing and comes out as-is, because it is the message that needs fixing, not the widget's job to dress it up. Links inside a bubble are styled by `.ep-contact-link` — a class that doubles as the click hook for the `contact_click` telemetry event (see TELEMETRY.md) — without it they would come out in the browser's default blue in the middle of the widget's palette.

### External attribution (UTM + dataLayer)

A click on a product card or a contact link makes the visitor **leave the widget for the shop's own site** — the point where the widget's own telemetry (`product_click`/`contact_click`, see [TELEMETRY.md](TELEMETRY.md)) stops being able to see what happens next: whether an order gets placed, or a contact form gets submitted. Closing that loop is necessarily the *shop's* job (their own GA4 property has to recognise the visit and later attribute a conversion to it) — the widget's job is only to hand it the breadcrumbs, via two independent, best-effort mechanisms that must never break a link that would otherwise have worked:

- **UTM stamping** (`withUtm(rawUrl, content)`) appends `utm_source=everyparts_widget`, `utm_medium=widget`, `utm_campaign=everyparts` and `utm_content=<'product_click'|'contact_click'>` to the outbound URL — never overwriting a `utm_*` the shop already put on `product.url` or `data-contact-page-url` themselves. This is what lets the shop's GA4 attribute a session, and later a purchase or a submitted contact form, back to `everyparts_widget` — standard UTM-based session attribution, no code needed on the shop's side beyond having GA4 installed. Applied once, at render time: `card.href` in `buildProductCard()`, and the `href` built by `linkTagHtml()` for every `[link]` tag. A URL that fails to parse (`new URL()` throws) is returned unchanged rather than breaking the link.
- **`dataLayer` push** (`pushDataLayer(payload)`) mirrors the same click as `{ event: 'everyparts_product_click', ... }` / `{ event: 'everyparts_contact_click', url }` into `window.dataLayer`, for shops already piloting GA4/GTM through it who want an event at click time rather than waiting on source/medium reports. Prefixed `everyparts_` so it can never collide with a same-named event the shop already defined with a different shape. It does **not** create `window.dataLayer` if absent — a shop with no GTM/gtag.js must not gain a stray global it never asked for — and the whole call is wrapped in try/catch: a missing, renamed, or hostile `dataLayer` must never be visible to the visitor as a broken click.

Both mechanisms read back the **already-stamped, live href** (`card.href`, `link.href`) rather than recomputing the URL — the same value the browser is actually about to navigate to.

**Outside this file, for the UTM half to be actually usable:** the shop needs GA4 (or whatever analytics they run) installed on their own site with UTM-based session attribution enabled — the default for GA4, nothing to configure — and, for the "did they buy/did they submit the contact form" question specifically, an actual conversion/ecommerce event wired up on their checkout or contact-success page. Without that second piece, the UTM parameters arrive but nothing on the shop's site turns them into a report. None of that is this repo's concern to build or verify — it's a one-time integration note to hand the shop when they enable the widget, not a widget feature.

### Coding rules

The widget presumes no business universe.
- No user-facing string, glyph or example names motorcycles, vehicles, tractors or appliances. The built-in `I18N` and `SUBJECT_ICON_PATH` are what a site gets before the hub says anything about it, so they have to fit every shop.
- What a universe calls its machines comes from the hub, per profile: `wordings` for the text, `icon` for the glyph. Adding a universe is a hub change, not an engine release.

Error handling: fail loud, never fake.
- Never suppress an error to look like it worked.
- Expose the failure; do not substitute placeholder data.
- A fallback is okay only if it's transparent.

Comments and this file describe the present, not the past.
- Say what the code does and how to use it — never what it used to do, what it replaced, or why a past alternative was rejected.
- A code comment explains the code and the surrounding structure only — never a cross-reference to another doc, a spec, or a discussion.
